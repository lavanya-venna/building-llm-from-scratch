## Design decisions and why

**Single language, public-data-only, no manual-collection quota.** The
assignment's rubric originally called for two languages (a higher-resource
"Model H" and a mandated lower-resource "Model L") and a ≥20% manual-collection
requirement. Both were dropped by explicit user decision early in the
project: only Hindi is being built, and the corpus is 100% public
Hugging Face data. Rejected alternative: building a Wikisource-scraping +
archive.org-OCR manual-collection pipeline was fully planned (see
`docs/worklog.md`'s early entries) before this scope cut — that plan was
abandoned, not implemented, once the manual-collection requirement was
dropped.

**Source priority: IndicCorpV2 (majority) → `zicsx/ai4bharat-hi-subset` →
`ai4bharat/sangraha` synthetic (last-resort fill).** Real, non-synthetic
text is preferred; Sangraha's synthetic split is used only to close
whatever gap the two real sources leave. Rejected alternative: Hindi
Wikipedia + IndicCorpV2 + mC4-hi was the original source list — Wikipedia
and mC4 were dropped by user decision in favor of the current three
sources (Wikipedia's corpus is small relative to IndicCorpV2 anyway; mC4
was the noisiest of the original three).

**OSCAR-2301 excluded.** It's a gated HF dataset requiring an authenticated
token with accepted terms; only a placeholder token (`your_...`) exists in
this environment, so it's inaccessible here. Not pursued further — the
three chosen sources cover the token target without it.

**SentencePiece Unigram over BPE.** Chosen for better fertility/UNK
behavior on morphologically rich Devanagari conjuncts. Not empirically
compared against BPE in this project — this is a documented judgment call,
not a measured result. `byte_fallback=true` was a hard requirement, not
optional, to guarantee the tokenizer can represent any input.

**`min_words_per_doc` lowered from 20 to 6.** See "Corrections" below —
this was a direct fix for the IndicCorpV2 document-reconstruction bug, and
6 was chosen as a value that keeps genuine short Hindi sentences (from
`ai4bharat_hi_subset`, which has no recoverable document boundaries) while
still dropping near-empty stub fragments. Not swept/tuned — a single
reasonable value, not the output of an experiment.

**`make_splits.py` deleted, not reimplemented.** During the `src/`
restructuring the user explicitly asked to remove the split-generation
script rather than migrate it, on the basis that "we can create splits
later." The already-generated `data/splits/{train,val,test}.jsonl` files
were kept (just relocated) — only the *script* that produced them is gone.
This is a deliberate gap: there is currently no code path to regenerate
splits from a changed corpus. If the corpus changes, a replacement split
script must be written before re-splitting is possible.

**Two separate reports, not one.** `report/dataset_stats.md` (corpus
collection/cleaning/dedup/split stats) and `report/tokenizer_eval_metrics.md`
(tokenizer vocab sweep, fertility, UNK rate, tokenization examples) are
generated by different modules (`src/data/data_preprocessor.py` and
`src/evaluation/tokenizer_eval.py` respectively) per explicit user
decision, rather than one combined report.

**Phase 2 — decoder-only Transformer, primitive PyTorch layers only.**
`src/model/model.py` implements `TokenEmbedding`, `PositionalEmbedding`,
`MultiHeadCausalAttention`, `FeedForward`, `Block`, and
`DecoderOnlyTransformer` using only `nn.Linear`/`nn.Embedding`/
`nn.LayerNorm`/`nn.Dropout` — no `nn.Transformer*`, `nn.MultiheadAttention`,
or HuggingFace classes. Architecture-only: just `__init__`/`forward` on
every class, no loss computation, no custom weight initialization, no
generation method, no training loop, no `train.py`. Code style/organization
adapted from
[hkproj/pytorch-transformer's `model.py`](https://github.com/hkproj/pytorch-transformer/blob/main/model.py)
(an encoder-decoder Transformer built the same primitive-layers way),
collapsed into a decoder-only shape.

**Pre-norm over post-norm.** Each sublayer normalizes its own input
(`x = x + sublayer(norm(x))`), keeping the residual stream itself
unnormalized end to end. Matches the reference file's `ResidualConnection`
pattern (which is already pre-norm) — no post-norm-to-pre-norm inversion
was needed, just `nn.LayerNorm` used directly instead of the reference's
custom `LayerNormalization` class, with residual adds inlined in
`Block.forward` per the task spec (no separate `ResidualConnection` class).

**No weight tying between `token_embedding` and `lm_head`.** Explicit task
requirement, kept as a deliberate simplification (see "Traced reasoning"
below for the real parameter-count cost this has at a 48k vocab).

**RoPE dropped, not stubbed — explicit user decision.** The original task
spec allowed `PositionalEmbedding`'s `type` to be `"learned"`,
`"sinusoidal"`, or `"rope"`. Real RoPE rotates Q/K vectors *inside*
attention using per-position angle tensors — it is not an additive
`(T, d_model)` term that can be added to token embeddings before the first
`Block`, which is the shape every other positional-embedding type in this
class produces. Implementing it "for real" would require changing
`MultiHeadCausalAttention`'s signature to accept rotation tensors, out of
scope for this phase. Two options were presented: (a) a labeled
additive stub using real RoPE frequency math but combined via concatenation
rather than true per-pair rotation (shape-compatible but not real RoPE), or
(b) drop RoPE entirely. User chose to drop it: `PositionalEmbedding` only
supports `"learned"` (default) and `"sinusoidal"`; any other value —
including `"rope"` — raises `ValueError`. Rejected alternative: the
labeled-stub approach, which would have been shape-compatible and
selectable but not mathematically real RoPE.

**`src/data/dataset.py`/`src/model/train.py` — reuse the existing
SentencePiece tokenizer and existing splits, don't build parallel ones.**
The literal task spec for these two files called for a brand-new
HuggingFace `tokenizers`-library (BPE/WordPiece) tokenizer trained on raw
per-source text, plus a freshly-derived 90/5/5 train/val/test split. Both
directly conflicted with real, already-completed work: `CLAUDE.md`'s hard
constraint ("tokenizer trained from scratch with `sentencepiece`"), Phase
1's already-selected 48k-vocab SentencePiece tokenizer
(`data/artifacts/hindi_unigram_48000.model`), and Phase 1's frozen,
source-stratified 98/1/1 split (`data/splits/{train,val,test}.jsonl`,
4,869,410/49,688/49,688 lines). Two options were presented: (a) build
exactly as literally specified, as a second, parallel, redundant tokenizer/
split coexisting with Phase 1's, requiring an amendment or documented
exception to `CLAUDE.md`'s hard constraint; or (b) adapt the same function
signatures/flow to reuse Phase 1's tokenizer and splits instead. **User
chose (b).** Concretely: `get_or_build_tokenizer` loads/builds a
`sentencepiece.SentencePieceProcessor`, not a HF `tokenizers.Tokenizer`;
`get_ds` reads the existing `data/splits/{train,val,test}.jsonl` directly
instead of combining raw per-source files and re-splitting; when the
tokenizer must be trained from scratch (fallback path only — the real
model already exists on disk), it trains on a sample of the **train split
only**, never val/test — matching Phase 1's actual practice
(`build_training_sample` only ever reads `train.jsonl`) and deliberately
improving on the literal spec's "train on all texts including val/test",
which would have leaked val/test docs into the tokenizer's vocabulary.
`config/model_config.yaml`'s new `dataset_paths`/`tokenizer_path` fields
were repurposed to point at the real existing artifacts rather than the
literal spec's placeholder per-source paths; `train_split`/`val_split`/
`test_split` were kept as config keys (per the literal request) but are
documented as unused by `get_ds` — the real split is Phase 1's frozen one.

**SentencePiece API surface differs from the literal HF-`tokenizers`-flavored
spec — verified against the real installed library, not assumed.**
`sp.get_piece_size()` (not `get_vocab_size()`, which does not exist on
`SentencePieceProcessor`); `sp.encode(text, out_type=int)` returns a plain
`list[int]` directly, no `.ids` attribute, no auto bos/eos; `sp.decode()`
accepts a `list[int]` but raises `TypeError` on a `torch.Tensor`, so
`HindiDataset.__getitem__` must decode from the pre-tensor slice, not the
tensor itself; `sp.eos_id() == 2`, `sp.pad_id() == -1` (pad disabled by
default on this model) — a non-issue since "concatenate and chop" needs no
padding, but an honest boundary against the literal spec's mention of a
`<pad>` special token, which does not exist in the reused tokenizer.

## Traced reasoning

**Why IndicCorpV2 needed document reconstruction.** The raw HF export
streams one sentence/paragraph-fragment per record, with a blank-text
record marking the boundary between original source documents — not one
document per record as initially assumed. First real pipeline run showed
IndicCorpV2 keeping only 3.43M of 9.96M records (65.6% dropped) at the
cleaning stage. Diagnosis: sampled 20,000 raw records directly — median
record length was **1 word**, many records were empty strings. The
`min_words_per_doc` filter was correctly rejecting these as "too short,"
but they were only short because they hadn't been reassembled into real
documents first. Fix: `regroup_paragraph_documents`/`regroup_file` in
`src/utils/reconstruct_documents.py` join consecutive non-blank records
into one document per blank-line gap. Applied once to the raw file,
collapsing 9,964,091 line-records into 4,982,046 real multi-sentence
documents. After the fix, cleaning-stage survival rose to ~96% for both
IndicCorpV2 and `ai4bharat_hi_subset`.

**`select_best_vocab`'s tolerance semantics.** `tolerance` is an absolute
difference in `avg_chars_per_token` from the best candidate in the sweep,
not a relative/percentage tolerance, despite superficially looking like
one in early test fixtures (values like 3.5/3.6/3.61 made both
interpretations coincidentally plausible until traced through explicitly).
Verified against real sweep data: 32k/48k/64k gave 4.261/4.345/4.390
chars/token; 64k is best (4.390); 32k's gap (0.129) exceeds the 0.05
tolerance and is excluded; 48k's gap (0.045) qualifies; of the qualifying
candidates {48k, 64k}, the smallest (48k) is selected.

**Why the full-size model is 42.3M parameters, not the ~25M originally
targeted.** With `config/model_config.yaml`'s `d_model=384`, `vocab_size=48000`
(filled in from the trained tokenizer), and no weight tying,
`token_embedding` (`48000 × 384` = 18,432,000) and `lm_head`
(`384 × 48000` weight + `48000` bias = 18,480,000) together account for
36,912,000 of the model's 42,333,312 total parameters — 87%. The six
`Block`s, `PositionalEmbedding`, and `ln_f` contribute the remaining ~5.4M.
This is a direct, mechanical consequence of two independently-fixed spec
choices (48k vocab, no tying), not a bug — confirmed via
`sum(p.numel() for p in model.parameters())` on the real config with a
manual forward-pass smoke test (`(4, 256)` int input → `(4, 256, 48000)`
logits). Flagged to the user; no change made, since both `vocab_size` and
"no weight tying" were explicit, unambiguous requirements. If the ~25M
target needs to be hit exactly, the two available levers are weight tying
(would land near ~24M) or shrinking `vocab_size`/`d_model` — deferred to
the user's call, not decided here.

**Why the word-count-to-token proxy overestimated the final corpus size.**
Collection budgets were set assuming `proxy_tokens_per_word = 1.4` (a
generic estimate). The real corpus's exact tokenizer-measured ratio
(486M final words → measured against the trained 48k-vocab tokenizer)
came out to **1.189 tokens/word** — the proxy overestimated by ~18%.
Consequence: the word-count-based collection stopped early (thinking it
had hit ~552M tokens' worth of raw words) but the exact final count was
**467,773,861 tokens**, about 6.4% under the ~500M target. User decision:
accept 467.8M as close enough to "~500M," not worth another ~hour of
recollection for a 6% gain.

## Honest boundaries

- **No manual-collection component exists at all** — not a partial
  implementation, a fully abandoned one. If a future rubric or version
  reintroduces that requirement, this is new work, not a resume-from-here.
- **467.77M tokens, not 500M.** Anything downstream that assumes exactly
  "~500M tokens" should use the real number.
- **`ai4bharat_hi_subset` almost certainly overlaps IndicCorpV2** (its
  first streamed record was byte-identical to IndicCorpV2's first
  record) — the ~26.8% combined dedup removal rate is doing real,
  necessary work, not just incidental cleanup. If a *fourth* overlapping
  source were ever added, dedup cost (currently ~90 min for near-dedup
  over ~5M docs) would grow accordingly.
- **No splits-regeneration script** (see above) — splits are currently a
  frozen artifact, not reproducible from the current codebase alone.
- **Language-ID filtering depends on a pretrained fasttext classifier**
  (`lid.176.bin`). This is explicitly permitted (it's a filter, not part
  of the model/tokenizer), but it means corpus composition is dependent on
  that external classifier's accuracy on Hindi/Devanagari-script text,
  which was not independently validated beyond spot-checking.
- **No model architecture, training loop, checkpointing, or evaluation
  exists yet.** This version is data + tokenizer only. *(Superseded in
  part by the Phase 2 session below: the architecture now exists, but
  training loop/checkpointing/evaluation still do not.)*
- **The model architecture is unit/shape-tested only, never trained.** No
  loss has ever been computed against it, so nothing about its actual
  learning behavior (does it converge, is the causal masking numerically
  well-behaved at scale, etc.) is verified — only that the tensor shapes,
  masking logic, dropout placement, and parameter-sharing contracts match
  the spec.
- **No weight initialization scheme.** `DecoderOnlyTransformer` and all its
  submodules rely entirely on PyTorch's default `nn.Linear`/`nn.Embedding`/
  `nn.LayerNorm` initialization — explicitly out of scope per the task
  spec, but worth knowing before training starts, since GPT-style models
  often use a custom scaled init (e.g. scaling residual-projection weights
  by `1/sqrt(2 * n_layers)`) that this implementation does not have.
- **RoPE is not available**, by explicit user decision (see "Design
  decisions" above) — only `"learned"` and `"sinusoidal"` positional
  embeddings work. A future phase wanting real RoPE will need to change
  `MultiHeadCausalAttention`'s interface, not just `PositionalEmbedding`'s.
- **42.3M parameters at the current config, not ~25M** — see "Traced
  reasoning" above. Not corrected; flagged to the user as an open question.
- **No training loop, loss, optimizer, scheduler, or checkpointing exists
  yet in `src/model/train.py`.** `train_model` builds the model and data
  loaders and stops at an explicit `# TODO` comment block sketching the
  shape of the loop (forward -> cross-entropy -> backward -> step ->
  per-epoch val eval -> resumable checkpoint) — none of it executes.
  Verified via a test that monkeypatches `DecoderOnlyTransformer.forward`
  to raise if called and confirms `train_model` still completes.
- **`HindiDataset.token_ids` is a plain Python `list[int]`, not a tensor or
  numpy array.** For the real train split this will be hundreds of millions
  of elements — several GB of Python int/list object overhead. Fine for
  this scaffold (nothing iterates the real train split yet), but a real
  training run should convert to a `torch.LongTensor`/`numpy` array first;
  not done here since it wasn't asked for and no training loop exists yet
  to make the cost concrete.
- **The reused tokenizer has no `<pad>` token** (`pad_id() == -1`,
  disabled) — see "Design decisions" above. Irrelevant to "concatenate and
  chop" (no padding needed), but would need addressing if a future padded-
  batching strategy is ever introduced.
- **`get_ds`/`tokenize_and_concatenate` tokenize an entire split's text in
  memory before batching begins** — no streaming/lazy tokenization. Fine
  at this phase's scale for val/test; for the full train split this is a
  real (if one-time, per-run) cost, consistent with the existing
  full-corpus-tokenization warning on `train.py`'s `__main__` block.
- **`.git` at the repo root was never removed**, despite an earlier
  explicit user request to do so (blocked by the harness's safety
  classifier as irreversible destruction, and never done manually since).
  A real commit (`8bff44c`) is already pushed to
  `git@github-personal:lavanya-venna/building-llm-from-scratch.git`.

## Debug / flag state

- **`numpy<2` pinned** in the venv — `fasttext-wheel` (unmaintained) is
  incompatible with NumPy 2.x's stricter array-copy semantics
  (`ValueError: Unable to avoid copy...`). This is a permanent pin, not a
  temporary workaround; do not upgrade numpy without re-verifying fasttext.
- **`HF_HOME` overridden** to `<repo>/.hf_cache_llm/` via a line appended
  to the venv's `bin/activate` script — the default `~/.cache/huggingface`
  is root-owned/unwritable on this box.
- **`config/tokenizer_config.yaml`'s `selected_vocab_size: 48000` is a
  committed decision**, not a placeholder — downstream code
  (`generate_tokenizer_eval_report`) fails loudly if this is null.
- **Long-running jobs are launched via detached `nohup ... & disown`,
  not the harness's `run_in_background`.** The latter has repeatedly
  (multiple separate incidents) killed real, correctly-running processes
  with a false "system is running low on memory" message despite
  terabytes of free host memory. This is a standing workaround, not
  resolved at the infrastructure level — anyone running long jobs in this
  repo should use the same pattern (see `CLAUDE.md`).
- **`torch==2.14.0+cu130` installed** into the project venv — CUDA
  confirmed available (`torch.cuda.is_available() -> True`) against the
  box's 4x H100 (driver 580.105.08). `requirements.txt` regenerated in
  full via `pip freeze` (not hand-appended), per `CLAUDE.md`'s "frozen
  `pip freeze` output" convention.
- **New environment quirk discovered this session: the root filesystem
  (`/`) is nearly full** (97G total, 95G used, ~2.1G free at time of
  writing) — unrelated to this project (large unrelated directories under
  `/home/lavanya.venna/`: `patram_standardization` 72G, `Environments` 66G,
  `miniconda` 42G, `training_models` 36G, and others). This caused the
  first `pip install torch` attempt to fail mid-download with
  `OSError: [Errno 28] No space left on device`, since pip's default cache
  (`~/.cache/pip`) and temp dir both land on `/` by default. **Workaround
  that worked**: `pip cache purge` plus redirecting both
  `PIP_CACHE_DIR` and `TMPDIR` to a new directory on the large `/fsxvision_new`
  mount (`/fsxvision_new/lavanya.venna/pip_tmp/{cache,tmp}`, 11T free at
  the time) before retrying the install. Anyone installing large packages
  (torch, CUDA wheels, etc.) in this environment should use the same
  redirect rather than assuming `/` has headroom — this is now a
  standing quirk worth checking before any large `pip install`, similar in
  spirit to the existing `run_in_background`/OOM-false-positive quirk
  above.

## Corrections

**Original: `min_words_per_doc = 20` for all sources.**
Failure mode: silently discarded ~65% of IndicCorpV2 because its raw
export is one-sentence-per-record, not one-document-per-record (see
"Traced reasoning" above).
Fix: added document reconstruction for IndicCorpV2 (recovers real document
boundaries) and lowered the threshold to `6` project-wide (since
`ai4bharat_hi_subset` has no recoverable boundaries and would otherwise
still lose most of its content). Both changes are in `config/data_config.yaml`
and `src/utils/reconstruct_documents.py`.

**Original: `download_public.py`'s IndicCorpV2 source entry used
`hf_config: hin_Deva`.**
Failure mode: `ValueError: BuilderConfig 'hin_Deva' not found` — IndicCorpV2
keys language by HF **split**, not config (its only config is
`indiccorp_v2`).
Fix: `hf_config: indiccorp_v2`, `split: hin_Deva`.

**Original: assumed the word-count-based proxy target (`target_total_tokens
/ proxy_tokens_per_word`) being reached meant ~500M real tokens were
collected.**
Failure mode: exact tokenizer measurement came in at 467.77M, ~6.4% short
(see "Traced reasoning" above).
Fix: none applied to the collection logic itself — user explicitly
accepted the shortfall rather than re-running collection. The proxy itself
(`proxy_tokens_per_word: 1.4` in `config/data_config.yaml`) was **not**
corrected to `1.189` — it remains the original estimate and would
overestimate again if reused for a future top-up.

**Original (mid-restructuring): ran
`python3 -m src.data.data_preprocessor` directly to spot-check that
import paths resolved correctly after the `src/`-layout move.**
Failure mode: that module's `__main__` block re-runs the *entire*
clean→exact-dedup→near-dedup pipeline from scratch, not a lightweight
import check. Caught mid-run and stopped, but it had already truncated
`data/processed/ai4bharat_hi_subset.stage1.jsonl` from 1,546,751 to
313,808 lines before being killed.
Fix: re-ran just `clean_and_filter_source` for that one file (not the
full `__main__`), reproducing the exact original counts (1,546,751 kept /
62,530 dropped-clean / 430 dropped-LID out of 1,609,711 total) — confirmed
no data was actually lost, just needed regenerating.
`indiccorp_v2.stage1.jsonl`, `deduped.jsonl`, `near_deduped.jsonl` were
untouched (the interrupted run hadn't reached those stages).
