# CLAUDE.md

Guidance for Claude Code (or any assistant) working in this repository.

## Project

Build a Hindi (Devanagari) large language model from scratch, one phase at a
time. Phase 1 — data collection, cleaning, and tokenizer construction — is
complete: ~4.97M documents, 467.77M exact tokens, a 48k-vocab SentencePiece
Unigram tokenizer, and a train/val/test split. Later phases (model
architecture, pretraining, evaluation) build on top of this.

Single language, single model. There is no multi-language scaffold here —
earlier iterations of this project considered a two-language (Hindi +
Assamese) setup; that was dropped. Don't reintroduce per-language directories
or assume the code needs to generalize across languages.

## Hard constraints

- **No pretrained models or tokenizers for the LLM itself.** Do not use
  `transformers.PreTrainedTokenizer`/`AutoTokenizer`, `torch.nn.Transformer*`,
  or any pretrained checkpoint as part of the model or its tokenizer. The
  tokenizer is trained from scratch with `sentencepiece` on our own corpus.
  The one exception is the fasttext `lid.176` language-ID **classifier** used
  purely to filter which documents enter the corpus (not part of the model or
  tokenizer) — this is called out explicitly in `report/dataset_stats.md`.
- **No `transformers` library model/tokenizer classes.** `datasets.load_dataset`
  is fine (it's just a data-access API, not a modeling class).
- **No large binary artifacts committed to git.** Raw/processed/split corpus
  files, tokenizer `.model`/`.vocab` files, and the downloaded `lid.176.bin`
  all live under `data/{raw,processed,splits,artifacts}/`, which is
  gitignored. Small samples (`data/visualize/`) and everything under `config/`,
  `src/`, `tests/`, `docs/`, `report/` are tracked normally.
- **Checkpoints (once training starts) must be resumable**: include model
  state, optimizer state, scheduler state, step count, and config.
- **Plots need a title, axis labels, and a legend.**
- **Modular, OOP-appropriate code split by concern** (data / tokenizer /
  evaluation / utils — see structure below), not one monolithic script.

## Project structure

```
llm_from_scratch/
  src/
    data/data_preprocessor.py   # cleaning, normalization, LID filtering,
                                 # pipeline orchestration (clean -> exact dedup
                                 # -> near dedup), dataset-stats reporting
    tokenizer/tokenizer_test.py # SentencePiece training (no pretrained tokenizer)
    tokenizer/tokenizer_config.py # get_config(): sweep settings (types, vocab
                                 # candidates) plus the selected production candidate
    evaluation/tokenizer_eval.py # fertility/UNK sweep, vocab selection,
                                 # tokenizer-metrics reporting
    utils/
      download_public.py        # streams/samples public HF datasets to a token budget
      reconstruct_documents.py  # fixes IndicCorpV2's one-sentence-per-record export
                                 # into real multi-sentence documents (see below)
      dedup.py                  # exact-hash + MinHash/LSH near-dedup primitives
      run_near_dedup_only.py    # standalone entry point to re-run just near-dedup
  data/
    raw/ processed/ splits/ artifacts/   # gitignored — regenerate, don't hand-edit
    visualize/                           # small tracked samples for eyeballing the corpus
  config/
    data_config.yaml       # sources, sampling budgets, seed, cleaning/dedup thresholds
  docs/
    worklog.md   # plain-language running log of what was done and why — append here,
                  # don't rewrite history
  tests/     # pytest, one test file per module, mirrors src/ layout
  report/
    dataset_stats.md          # corpus/cleaning stats — generated by data_preprocessor.py
    tokenizer_eval_metrics.json # (vocab_size, model_type) -> {fertility, unk_rate} sweep — generated by tokenizer_eval.py
  requirements.txt
```

## Environment

- **venv, not conda.** The project venv lives at
  `/fsxvision_new/lavanya.venna/environments/building_llm_from_scratch`
  (created with `virtualenv`, not the stdlib `venv` module — this box's
  Python lacks `ensurepip`, so `python3 -m venv` fails; `virtualenv` doesn't
  need it). Activate with
  `source /fsxvision_new/lavanya.venna/environments/building_llm_from_scratch/bin/activate`.
- `requirements.txt` is the frozen `pip freeze` output — refresh it after
  installing anything new.
- `numpy` is pinned `<2` — `fasttext-wheel` (used for language-ID filtering)
  is unmaintained and crashes under NumPy 2.x's stricter array-copy semantics.
- `HF_HOME` is set to `<repo>/.hf_cache_llm/` via a line appended to the
  venv's `bin/activate` script. The default `~/.cache/huggingface` is
  root-owned and not writable on this box; a sibling path
  (`/fsxvision_new/lavanya.venna/hf_cache`) turned out to already exist as an
  unrelated root-owned shared cache — don't reuse paths outside this repo for
  HF cache.

## Known environment quirks

- **Backgrounded long-running jobs sometimes get killed with a false
  "system is running low on memory" message**, even when the host has
  terabytes free. This has hit `run_in_background: true` Bash calls and
  auto-backgrounded (timeout-exceeded) calls alike. Workaround that has
  reliably worked: launch as a **detached** process instead —
  `nohup python3 -m some.module > /tmp/log 2>&1 < /dev/null & disown` — and
  poll the log file or use the Monitor tool rather than the harness's
  background-job tracking. No code changes were ever needed; it's purely
  about how the process is launched.
- **Heavy `__main__` blocks**: `src/data/data_preprocessor.py`'s `__main__`
  re-runs the *entire* clean → exact-dedup → near-dedup pipeline from
  scratch (multi-hour on the full corpus). Don't run
  `python3 -m src.data.data_preprocessor` just to sanity-check imports or
  paths — import the specific function you need
  (e.g. `generate_dataset_stats_report`) in a `python3 -c` one-liner instead.
  Same caution applies to `src/tokenizer/tokenizer_test.py`'s and
  `src/evaluation/tokenizer_eval.py`'s `__main__` blocks (tokenizer training
  and full-corpus retokenization, respectively — both real work, not free).

## Data provenance and a real bug worth knowing about

Final corpus sources, in priority order: **IndicCorpV2** (majority) →
**`zicsx/ai4bharat-hi-subset`** → **`ai4bharat/sangraha`'s `synthetic/hin_Deva`**
(last-resort synthetic top-up; ended up contributing ~110M raw words since the
first two sources alone landed under the ~500M-token target after cleaning +
dedup). `oscar-corpus/OSCAR-2301` was considered but is gated with no valid HF
token available here.

**`reconstruct_documents.py` exists because of a real data-quality bug**:
IndicCorpV2's raw HF export streams **one sentence per record**, not one
document per record, with a blank-text record marking where one source
document ends and the next begins. The generic length filter
(`min_words_per_doc`) was silently rejecting ~90% of records because each one
was a single short sentence — even though the underlying text was fine prose
once reassembled. `regroup_paragraph_documents`/`regroup_file` fix this by
joining consecutive non-blank records into real documents. `ai4bharat-hi-subset`
has the same one-sentence-per-record shape but its blank-line boundaries were
already stripped upstream, so it's unrecoverable there — `cleaning.min_words_per_doc`
in `config/data_config.yaml` is set low (6) partly to accommodate this.

`ai4bharat-hi-subset` also appears to be a rehosted subset of IndicCorpV2
(byte-identical first records) — expect and don't be alarmed by a high dedup
rate against it; it's already accounted for in `report/dataset_stats.md`.

## Conventions

- **Test-first.** Every function in `src/` has a corresponding test in
  `tests/` written before (or alongside) the implementation. Run the full
  suite with `pytest tests/` from the repo root before considering any change
  done.
- **Docstring convention for cleaning/normalization functions**
  (`src/data/data_preprocessor.py`): one function per transformation, with a
  docstring explaining *what* it does, *why* it matters for this corpus, and
  a concrete before/after example — not just a description of the code.
- **Docstring convention everywhere else: terse.** One sentence on what the
  function does, then an `Args:` line and a `Returns:` line — no rationale
  paragraphs, no before/after examples, no restating what well-named
  parameters already make obvious. This is the default for `src/tokenizer/`,
  `src/evaluation/`, `src/model/`, and `src/utils/`; the fuller what/why/example
  style above is scoped specifically to `data_preprocessor.py`'s
  cleaning/normalization functions, not a repo-wide default.
- **Reproducibility**: seeded RNGs everywhere sampling/splitting happens
  (`config/data_config.yaml`'s `seed`), idempotent collection scripts (skip
  re-fetching a source if its output file already meets budget).
- **`docs/worklog.md`** is a plain-language, append-only running log —
  what was done, what broke and how it was fixed, concrete outcomes. Update
  it as work happens, not retroactively. Don't rewrite past entries to "clean
  up" history.
